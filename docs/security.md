# Security and known limits

Forge protects a single team's private artefacts and management credentials from anonymous visitors, other sites and revoked users. It trusts the Cloudflare account operator, configured identity providers, administrators and publishers. It is not a sandbox for third-party HTML, a tenant-isolation boundary or a way to recall bytes someone already received. To report a vulnerability privately, see [SECURITY.md](../SECURITY.md).

## Browser origins and bearer links

- **Separate origins, not separate sites.** Management does not serve artefacts as web content; authorized MCP clients can read file text. Host-only cookies and a strict manage CSP (including `frame-ancestors 'none'`) limit cross-origin access. SameSite alone does not stop a sibling read host sending requests: cookie-authenticated writes require the exact manage `Origin`. MCP rejects browser origins outside its configured allowlist. Never add the read origin to that allowlist or put management and artefacts on one origin.
- **Artefacts share one read origin.** Artefact JavaScript acts with the viewer's read access. It can also sign the browser into another read session (read-host login CSRF). There is no separate read-host logout: sign out on the manage host. Only trusted publishers should upload HTML. Do not publish untrusted third-party HTML; per-artefact origins would be needed to isolate it.
- **Share URLs are bearer secrets.** Generated keys have 128 random bits; only admins can import a custom key. Forge hashes keys for lookup, keeps revoked keys reserved while their records exist and seals the revealable copy with AES-256-GCM bound to link and artefact IDs. `Referrer-Policy` helps by default, but artefact HTML can override it, scripts can read their own URL and platform request logs can record paths. A recipient can forward the link until revocation. Avoid capturing bearer paths in Cloudflare logs; treat their history as sensitive.
- **Invite and upload URLs can also leak through paths.** Invites authorize one admission until used, revoked or expired; upload URLs authorize one PUT attempt until claimed or expired. Neither is meant for logs or analytics. API tokens are 256-bit bearer secrets, shown only once, stored as hashes and revocable; use separate bot tokens with the least privilege needed.

Private handoff codes are short-lived and sent in a manage-origin form POST, not in a URL. Codes are consumed once, even if browser binding fails. Binding failures (including racing initial tabs) can require restarting navigation from the read host. Browsers with strict cross-origin cookie policies may block the handoff state. There is no cross-artefact authorization inside a publisher's own origin. Downloaded copies cannot be revoked.

## Operator theme

Theme files are trusted operator content shipped with the Worker, not publisher uploads. Use a dedicated assets directory with `run_worker_first: true`; Forge serves only the supported file types from `/_theme/` on each configured origin, with `nosniff` and the existing SVG sandbox CSP. Do not put secrets or untrusted files in this directory. CSS, images and fonts on Forge-authored pages are restricted to the page's own origin.

Ordinary manage HTML adds only `font-src 'self'` to the existing policy. Forge-authored read HTML, which previously had no CSP, now has a restrictive CSP with same-origin styles, images and fonts. The manage-to-read handoff also allows same-origin styles and fonts while retaining its exact script hash and form target. These policies apply to Forge's own pages, including its errors, not to published files or artefact redirects.

## Manage UI forms and one-use notices

- **Stale forms:** mutating forms require the exact manage origin, an active session and live core authorization. Form bodies are limited to 32 KiB. Slug-keyed artefact forms bind the displayed stable ID to the slug so a stale form cannot change a replacement artefact.
- **One-use flashes:** after a mutation, a 303 redirect carries a random, non-secret `flash-id`, never an API token, invite URL or share key. An eligible document navigation atomically consumes the D1 row within two minutes, with the original session, current role and exact destination path and query. Silent OIDC revalidation may intervene. Separate IDs let tabs continue independently.
- **One-time display is not revocation:** secrets are sealed in D1 using a dedicated key derived from `FORGE_COOKIE_KEY`, are not written to audit logs, and are removed from the page when it is restored from the back/forward cache. A missed or expired API-token flash does not revoke its token; revoke it and issue another rather than looking for the secret in logs. For shares, explicitly reveal an active link again. Browser copies cannot be recalled.
- **Referrer policy:** management pages use `Referrer-Policy: same-origin` to keep continuation URLs off other origins while preserving the `Origin` on same-origin form posts. Responses with no form submission, such as invitation-entry redirects, may be stricter. This does not hide paths from same-origin infrastructure or platform logs; keep request URL logging off where possible.

## Identity and OAuth

Forge binds sign-in flows to the initiating browser, uses PKCE S256 and OIDC nonce, verifies issuer, audience and required claims, and denies access on provider or D1 failure. Credentials never grant a permanent role: membership, generation and revocation are checked in D1. Keep DCR off unless a required client needs it. The Forge-hosted local CIMD is only a generic description, not a verified local client identity; check the displayed loopback port when approving.

- **Back-channel logout is best effort.** Without a logout notification a browser session can survive until OIDC revalidation or its absolute cap. If the IdP session ends without notifying Forge, a grant can survive until subject-wide revocation, member removal or the seven-day grant end. Disabling OIDC freshness checks makes the browser session depend more on logout notifications and its cap.
- **GitHub is not revalidated.** GitHub OAuth sign-in lacks silent OIDC revalidation and back-channel logout. Barring local revocation, browser sessions can survive upstream access loss until their configured absolute cap.
- **Refresh race.** The provider continues to accept the previous refresh token until the new token is first used and does not detect reuse during that interval. The absolute seven-day grant cap bounds a stolen refresh token.
- **Replay-marker outage.** A validated authorization-code replay normally writes a durable D1 denial marker that blocks exchange, refresh and calls even if KV state lags. If every marker write fails, denial depends on KV grant deletion. Other locations can see a stale grant for 60 seconds or more; a refresh from a stale location can re-create the grant until another revocation or the seven-day cap. A failed KV deletion has the same outcome. This combined failure requires the original code exchange and PKCE verifier. Issuance that fails partially or ambiguously requires new authorization.

## Storage and purge

- **Read consistency.** A browser that loads assets while publishing may get files from two revisions. Only single byte ranges are supported; malformed, multipart or unsupported ranges fall back to whole responses.
- **Hash reuse trusts the publisher.** `create_uploads` may return `alreadyStored` for a referenced hash and matching size. Knowing or guessing a digest does not prove possession; a publisher could republish those bytes and change who can read them. Do not give publisher access to untrusted parties.
- **Abandoned bytes.** Expiring upload rows and pruning revisions remove D1 metadata, not blob objects. Purge cannot find bytes whose last artefact association was already pruned, nor bytes protected by a stored upload that later expires unused. An interrupted PUT cannot reuse its capability. Verification copies can survive until their required one-day R2 expiry plus asynchronous deletion (usually within a further 24 hours). Never put an age-based lifecycle rule on `blobs/`.
- **Out-of-band deletion.** An R2 object removed outside Forge can still be referenced in D1. Republishing the same bytes may skip an R2 write because of deduplication; treat the missing object as an operator incident and restore it from backup.
- **Fence conflicts.** A purge advances a D1 epoch; an overlapping inline publish or upload verification may receive a retryable conflict even for unrelated bytes. Request a new upload capability if a PUT has already started.
- **Late R2 delete.** Purge holds a 15-minute attempt lease. If a delete is still outstanding after the lease, a successor can take over. If the same bytes are republished after the successor releases its claim but before the original delete lands, the late delete can remove the new object. Do not purge during mixed-version rollout or roll back to a Worker without the fence. Keep backups; soft deletion is not a backup.
- **Bounded maintenance is not a deletion SLA.** One daily event advances at most three purge steps; a large artefact or backlog can take multiple days after eligibility. Expired credentials are unusable whether or not their rows have been swept. See [maintenance](architecture.md#maintenance) for cutoffs.
